# Remaining Work: Frontend, Server, and Dashboard Separation

This document records exactly what remains to finish the requested restructuring. It is based on the current repository state and does not describe work that has already been completed.

## Current State

The application already has a logical separation of responsibilities:

- Public HTML pages and `config.js` form the public website.
- PHP API files under `api/` contain authentication, database access, domain logic, form ingestion, command handling, and realtime events.
- `dashboard/` contains the administrator interface.
- The dashboard communicates with the backend through authenticated REST requests and Server-Sent Events (SSE).
- The database is accessed by PHP only.
- The old Telegram bot is no longer an active communication mechanism.

The requested architecture is still incomplete because the public website and backend are not physically separated into `frontend/` and `server/`, and the current paths and deployment configuration assume that all three areas are hosted together at the repository root.

Create:

```text
server/.env

```

Do not commit `server/.env`.

The current `api/config.php` contains configuration directly in PHP. It must be changed so private deployment values come from environment variables or an equivalent server-only configuration mechanism.

At minimum, externalize:

```text
APP_ENV=production
DATABASE_URL=
DATABASE_USER=
DATABASE_PASSWORD=
SESSION_SECRET=
JWT_SECRET=
PUBLIC_ORIGIN=https://www.example.com
```

Only variables actually required by the PHP implementation need to be used. For example, `PORT` is unnecessary when Apache or PHP-FPM owns the HTTP listener, but the deployment documentation must state this.

- Database credentials
- Session secrets
- Password seed configuration
- Private signing keys
- Internal filesystem paths
- Database DSN
- Admin bootstrap data

The frontend and dashboard must never be given the server `.env` file.

## 6. Update Routing and Web Server Configuration

The current root `.htaccess` assumes these paths exist at the repository root:

```text

/dashboard

```

After restructuring, update routing for the selected deployment model.

### Recommended deployment model


This model gives each component a clear origin and independent deployment boundary.

## 7. Decide and Document the Realtime Transport

The current implementation uses Server-Sent Events:

```text
Dashboard -> REST API for actions
Dashboard <- SSE stream for realtime updates
```

The implementation is in:

- `api/stream.php`
- `api/_events.php`
- `dashboard/assets/app.js`

SSE is suitable for the current shared-hosting design, but the requested prompt mentions WebSocket or Socket.IO. One explicit decision is still required:

### Option A: Keep SSE

Keep the current implementation and document that SSE is the approved realtime transport because:

- It works with Apache and shared cPanel hosting.
- It requires no long-running Node process.
- Dashboard writes already use ordinary authenticated REST requests.
- The stream is bounded and reconnects automatically.

### Option B: Replace SSE

Implement WebSocket or Socket.IO support, including:

- A long-running server process
- Connection authentication
- Event authorization
- Reconnection handling
- Deployment supervision
- Reverse proxy configuration
- Production process monitoring

The current repository does not contain WebSocket or Socket.IO infrastructure.

The frontend currently receives administrator commands by polling `poll_commands.php`, not through a realtime socket. This must be documented or changed if frontend realtime delivery is a requirement.

## Final Completion Criteria

The task is complete only when all of these statements are true:

- `frontend/`, `server/`, and `dashboard/` are separate top-level areas.
- Frontend contains only public website code and public configuration.
- Server contains all API, authentication, database, storage, and realtime code.
- Dashboard contains only admin UI code and server communication code.
- Frontend communicates only with the server.
- Dashboard communicates only with the server.
- Database access occurs only inside the server.
- No relative frontend-to-API assumption remains.
- No relative dashboard-to-API assumption remains.
- Server secrets are loaded from server-only configuration.
- CORS, cookies, CSRF, and SSE work for the chosen deployment topology.
- The realtime transport decision is documented and implemented.
- Telegram code, credentials, and active legacy runtime dependencies are removed.
- Temporary development files are removed from production.
- All existing public flows and dashboard workflows pass verification.
- Deployment instructions match the actual final folder structure.

Until these criteria are met, the project has a working logical separation but not the complete physical and deployment separation requested by the task.
